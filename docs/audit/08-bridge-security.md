# Security review of the desktop bridge and UI

Scope: `chord-desktop/src-tauri/src/*.rs`, `tauri.conf.json`, `capabilities/default.json`, and the Svelte UI in `chord-desktop/src/lib`. This was a read-only review. No code ran. Runtime behaviour of the webview is marked "Unverified" where it applies.

## Summary

- The bridge is in good shape. The SSRF filter, the emoji pack checksum, the secret handling and the xmpp: link confirmation are all well built. There is no `{@html}`, no `innerHTML` and no `eval` in the UI.
- Two commands trust the UI for file paths: `upload` reads any file and `save_image` writes any file. A single UI script bug (for example through a theme) would turn into arbitrary file read or write. Both commands need a check that the path came from the system dialog.
- The webview loads remote media directly. `img-src https:` and `media-src https:` let any message sender or any imported theme make the user's IP address contact any https host. This bypasses the "Show link previews" switch and the Rust SSRF filter.
- An imported theme that has a link is fetched again on each launch with no new consent. The author can change the CSS later. CSS `url()` can send requests to any https host.
- The attachment file card uses an `<a href download>` with no `target`, and the URL comes from the sender (XEP-0066). Unverified: a click can navigate the main window to a remote page.
- The KLIPY key is compiled into the binary in clear text. Error messages do not leak it. The key is not in git.

## Already done well

- SSRF filter (`link_preview.rs`): the custom resolver `PublicOnly` drops non-public addresses at connect time, so DNS rebinding fails. It handles IPv4-mapped, NAT64, IPv4-compatible and 6to4 IPv6 forms. `validate_url` checks IP literals. The URL crate turns `2130706433` and IDN names into a canonical form. Each redirect goes through `validate_url` and stops after 3 (`shared_client`). Proxies are off, so no proxy DNS bypass. No user info in URLs. There are unit tests for all of these.
- Size and time caps: page 512 KB, image 50 MB, theme 256 KB, GIF answer 2 MB, settings 256 KB, upload 100 MB. Timeouts are 10 s and 5 s connect (120 s for image download). reqwest has no `gzip` feature, so there is no decompression bomb.
- Theme fetch (`theme_fetch.rs`): https only, content type must be text and not `text/html`, and the final URL must be https.
- Secrets: the keychain (`keychain.rs`) has a native store on each OS and a fitted error text. `SessionConfig` hides the password in `Debug`. The GIF error path never prints the URL (`gif.rs:request_error`). `.gitignore` covers `dev/klipy/.env`, `dev/prosody/.env` and `dev/foid/.env`. Only `.env.example` is tracked, and it holds placeholders. I found no key, token or password in the tracked files.
- Emoji packs (`emoji.rs`): fixed URL and fixed SHA-512 (`verify`). No redirects. `is_hex_key` restricts file names, so path traversal fails. The scheme serves SVG with `default-src 'none'` and `nosniff`, and the UI uses `<img>`, so no SVG script runs. The tarball reader takes only two named entries and caps each at 160 MB.
- Custom schemes: `chord-avatar` uses SQL parameters, not file paths. It refuses non-image mime types and sends `nosniff`. `chord-emoji` splits and validates the path.
- Markdown (`MessageBody.svelte`, `markdown.ts`): tree rendering with Svelte markup, no `{@html}`. Only http, https and known xmpp: forms pass `linkable`. Links use `rel="noopener noreferrer"`. `openLink` (`attachments.ts:62`) allows only http, https and mailto.
- Deep links: `xmppLinks.open` always shows `XmppLinkModal`. Nothing joins, adds or sends until the user clicks. The `chat` link opens an empty box and does not send `body`. Links are length-capped (2048) and control characters are refused. Repeat links from macOS are de-duplicated. `xmpp://authority` links are refused.
- `send_link` allows https only. `set_avatar` caps size at 1 MB and needs an `image/` mime. `gif.rs` drops ads and non-https media URLs.
- Capabilities: no `fs`, `shell`, `http` or `process` plugin. No `remote` capability, so a remote page in the webview gets no IPC. `withGlobalTauri` is off. `dialog:allow-open` and `allow-save` only. `deep-link:default` does not include register.
- CSP: `connect-src` has only `ipc:`, so page script cannot `fetch` out. `style-src` blocks remote CSS. `font-src 'self'`. `default-src 'self'` blocks inline script and `javascript:` links.
- The browser preview build (`vite.preview.config.js`, `preview/`) uses sample data and no network in `live = false` mode. It has no key.

## Recommended next steps

1. Bind `upload` and `save_image` to dialog paths (BRIDGESECURITY-01, 02). Effort: 3 to 5 hours.
2. Stop automatic remote loading from strangers, or proxy media through Rust with the SSRF resolver (BRIDGESECURITY-03, 04). Effort: 1 to 2 days.
3. Fix the attachment `download` link and add an `on_navigation` guard (BRIDGESECURITY-06). Test on macOS, Windows and Linux. Effort: 2 to 3 hours.
4. Add a consent step when a linked theme changes, and warn that themes can send requests (BRIDGESECURITY-05). Effort: 0.5 to 1 day.
5. Put the KLIPY key behind a small proxy (BRIDGESECURITY-07). Effort: 0.5 to 1 day.
6. Check that TLS verifies the JID domain when `server` is set, and drop `opener` reveal permission (BRIDGESECURITY-08, 09). Effort: 2 to 4 hours.
7. Harden the CSP, add a CSP header to `chord-avatar`, restrict avatar mime types (BRIDGESECURITY-10, 11). Effort: 1 to 2 hours.
8. Add a confirmation for masked links, punycode display in the xmpp: dialog, a fetch semaphore, and `cargo audit` / `npm audit` in CI (BRIDGESECURITY-12 to 16, 20). Effort: 0.5 to 1 day.
