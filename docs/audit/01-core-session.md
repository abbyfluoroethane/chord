# RFC 6120 and RFC 6121 core session audit

Scope: chord-core/src/session/, actor.rs, features/mod.rs, disco.rs, roster.rs, presence.rs, carbons.rs. I also read the tokio-xmpp 6.0.0 and sasl 0.5.2 sources in the local cargo registry. This audit is read only. No build ran and no server was contacted.

## Summary

- The session layer is solid. STARTTLS is mandatory, certificate errors are separate, SASL errors decide retry or stop, and XEP-0198 resume comes from tokio-xmpp. Unknown IQ requests get `service-unavailable`.
- One MUST is broken. Chord sends `ver=""` in the roster get without a check for the `rosterver` stream feature (RFC 6121 2.6.2).
- Chord cannot reach servers that offer only direct TLS. It does not use XEP-0368 or the `_xmpps-client._tcp` SRV record, although tokio-xmpp has both.
- The client does not use CSI (XEP-0352), a client ping (XEP-0199), XEP-0092, XEP-0202, or XEP-0012. Dead connections take up to 10 minutes to detect.
- The disco#info answer and the caps hash omit many features that Chord really uses (chat markers, reactions, corrections, retraction, replies, fallback, OOB, hints, direct invites).
- SASL is limited: SCRAM-SHA-256 and SCRAM-SHA-1, with -PLUS on TLS 1.3 only. XEP-0440 is not read. There is no SCRAM-SHA-512 and no SASL2 (XEP-0388).

## Already done well

- STARTTLS is mandatory. A server with no STARTTLS gives `NoTls`, and there is no plain text path in release builds (tokio-xmpp starttls.rs:41-73). The `dev-insecure` feature is gated (chord-core/Cargo.toml).
- Certificate errors are separate from other errors and are not retried (native.rs:557-582, session/mod.rs:141-149). The certificate is checked against the JID domain.
- SRV lookup for `_xmpp-client._tcp` with fallback to the domain (native.rs:96).
- SASL: SCRAM-SHA-256 and SCRAM-SHA-1 come before PLAIN. The gs2 flag is `y` when the client supports binding but the server offers no -PLUS, so a downgrade is detectable (native.rs:487-496, sasl common/mod.rs:172-181). Failure conditions map to retry or stop (session/mod.rs:118-134). A fatal failure on reconnect stops the loop and tells the UI (native.rs:200-212).
- Reconnect with exponential backoff from 1 s to 30 s, a timeout for each attempt, and a clean shutdown (native.rs:160-263). The slot panic of tokio-xmpp is handled (native.rs:270-330).
- XEP-0198: `<enable resume="true"/>`, acks and resume are handled by tokio-xmpp. Chord separates `resumed` from a fresh session, and skips the re-sync on resume (features/mod.rs:230-236, actor.rs:788-800).
- IQ handling: every unknown get or set gets `service-unavailable` with type `cancel`. Results and errors with no pending entry are never answered (features/mod.rs:186-206). Answers are matched by id and by the `to` address of the request (mod.rs:73-88, actor.rs:864-880). Pending IQs time out after 60 to 75 s (actor.rs:44-46, 731-756).
- Ping request from the server is answered (features/mod.rs:210-219). The logout uses a ping as a barrier so queued stanzas are delivered (actor.rs:557-583).
- Roster: get, push, `ver` storage, remove, one item per push, sender check on push, pre-approval with the `urn:xmpp:features:pre-approval` feature, and the `ask` and `approved` flags (roster.rs). Subscription request, approve and deny work (roster.rs:344-355, 483-518).
- Presence: initial presence with caps, show and status. Presence is stored for each resource and cleared on a fresh session (features/mod.rs:243-246, roster.rs:461-517).
- Caps (XEP-0115): SHA-1 hash from `compute_disco`, and the same info answers disco#info (disco.rs:38-53).
- Carbons: enable at connect, and forged carbons from other senders are dropped (carbons.rs:22-51).
- The password is hidden in `Debug` output (session/mod.rs:52-62).

2. Fix CORESESSION-08 and 09: complete the disco feature list, add a test that guards it, and answer nodes and disco#items correctly. About 3 hours.

6. Keep the send token and report delivery failure to the UI (CORESESSION-13). Test a crafted bad stanza for CORESESSION-12. About 1 day.
